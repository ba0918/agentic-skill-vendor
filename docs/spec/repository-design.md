# リポジトリ設計

このリポジトリの設計上の決定事項を記す。実装の手順や順序は実装計画側の管轄であり、
ここには「何を作るか・何を不変条件とするか」だけを置く。

## 目的と責務境界

本リポジトリは、スキルリポジトリ向けの共有参照文書 vendoring ツールを提供する。
ツールの責務は次の2点のみとする。

- **配布**: 正本の共有文書を各スキルの配下へ決定論的に生成・展開する
- **同一性保証**: 配布先コピーが正本とバイト同一であることを digest で証明し、
  未承認の drift を検出する

互換性判定・退行検知は責務に含めない。digest が証明できるのは決定論的生成の
同一性のみであり、そこから「新しい版が既存スキルと互換である」ことは導出できない。
証明できないことをツールに保証させない。互換性の判定は消費側リポジトリの
regression 機構の責務とする。

ただしこの責務二分が成立するためには、承認操作(accept)の側に互換性の証拠を
束縛できる結合点が必要である。regression 証跡は旧・新両方の digest を含み、
accept はその証跡を採用対象の digest に束縛できる形を保つ。pass/fail だけの
記録では「別の版間で成功した証跡を根拠に第三の版を採用する」取り違えを防げない。

## 宣言と pin の分離

スキル側の宣言は SKILL.md frontmatter に契約 id のみを書く。digest は書かない。
digest pin は中央の lock ファイルに置く。

宣言は「安定した依存の意図」、pin は「現在の採用内容」であり責務が別である。
id-only 化により、契約更新時に参照スキルの SKILL.md に diff が発生せず、
スキル読込のたびに消費される無関係トークンも消える。

## lock ファイルの正規形

lock は次の2区分を論理分離した正規形とする。

- dependencies: スキル → 契約 id 列
- resolutions: 契約 id → digest(および conformance digest)

混在させると「依存追加」と「契約更新」が同種の diff に見えるため分離する。
version フィールドは表示専用に降格する(削除はしない — 互換性判定には既に未使用の
opaque 文字列であり、削除は不要な破壊的変更になる)。ファイル名と JSON schema の
細部は実装計画で確定する。

同一 id の意味再利用はツールには判定できないが、採用履歴を消してはならない。
lock の git 履歴がその最低線である。

## accept — 承認境界

pin の更新と再生成を行う accept コマンドを承認境界として設ける。

- accept は routing metadata(契約 id × 旧新 digest × 直接依存スキル一覧)を
  機械導出して提示する。影響一覧は依存グラフの正本(lock)を持つツール側が
  導出することで drift を生まない
- accept-all は提供しない
- CI は accept を実行しない。CI の役割は未承認 drift の検出と fail のみ

意図的採用を守るのはコマンドの不便さではなく、accept 時にレビュー可能な情報が
作られることである。

## vendored copy のヘッダ

生成物には編集禁止の表示(DO NOT EDIT)・契約 id・正本 digest を付す。
契約本文を読むとき1回だけの消費であり、コピー単体の識別・破損検出に意味がある。
機械検証専用データを SKILL.md から追い出し、生成物側に残す情報配置である。

## 実装言語と配布

実装は Deno/TypeScript とする。ソースは責務ごとのモジュール(src/)に分割し、
テストは各モジュールに隣接して置く(`src/{name}.ts` + `src/{name}.test.ts`)。
CLI の入口はルーティングに徹し、ロジックを持たない。

配布はソースのまま行う: 利用側は src/ のモジュール群を自リポジトリに取り込んで
commit し、`deno run` で実行する。単一ファイルへの結合・`deno compile` などの
配布用生成物は持たない — 生成物を持つと、その生成の再現性という新しい検証対象が
生まれる。取り込んだコードの改変・更新は、利用側リポジトリの git と通常の
コードレビューで見える。

依存は最小に保つが、確立した形式の解析は自作しない。frontmatter の解析は
エコシステムの標準実装(@std/yaml)を厳格設定で採用し、その上の検証層
(宣言スキーマの強制)だけを自前で持つ。手書きの制限文法パーサは「読めない
入力を黙って空として受理する」欠陥クラスを自ら再発明することが実測で示された
ため採らない。

## セキュリティ不変条件

実装は次の不変条件を常に満たす。

- symlink による走査境界の逸脱を拒否する
- 生成物の書き込みは原子的に行う
- 同一性検証はバイトレベルの走査で行う

(これらを TDD で先行して固める進め方や、agentic-meta で試作された旧 Python 実装の
テスト群を互換性契約ではなく境界条件チェックリストとして参照する規律は、
実装計画側で扱う。)

## 安定保証面(外部互換性)

verify がバイト同一比較である以上、次はすべて外部互換性そのものであり、
安定保証面として扱う。

- CLI・manifest schema・exit code
- digest アルゴリズム・正規化規則
- conformance ツリーの framing 規則
- vendor ヘッダのバイト形式
- violation kind

Python API / TypeScript API の公開は、要求が観測されるまで行わない。

## 抽出境界

| 本リポジトリ | agentic-meta に残留 |
|---|---|
| ツール本体 | 契約の実内容 |
| ツールのテスト | skillset-alpha / beta(meta 側の合格条件測定器) |
| ツール検証 fixture(contracts-basic 相当) | 消費側 CI 配線 |
| 仕様文書 | 取り込んだツールの pin と出所記録 |
| ツール自身の CI | |

contracts-basic はツールの状態遷移を検査する fixture であり、ツール側の関心である。

## 消費方式

利用側はツールのソース(src/)を自リポジトリに取り込んで commit する。取り込んだ
コードの完全性は利用側の git と通常のコードレビューが担い、CI でツール自体を
照合する専用機構は置かない — ツールのコピーを改ざんできる者は照合値も CI 設定も
同じ権限で書き換えられるため、照合は防御として機能しない。

ツールの更新で守る原則は 1 つ: 新しい版を古い版のツールに承認させない
(bootstrap 循環の回避)。これは CI ゲートではなく更新フローの原則であり、
更新は通常の依存更新として人間が diff をレビューして取り込む。

self-test は完全性検証ではなく、実行環境でツールが正しく動くことのスモーク
チェックとして提供する。実行するかは利用側の任意。

provenance にはツールの出所・契約本文の出所(source identity)を表現できる
schema を持たせ、更新レビュー時のメタデータとして用いる。

## lint-selfcontain の位置づけ

スキルディレクトリの自己完結性検査(lint-selfcontain)は「配布」でも
「同一性保証」でもない第3の責務(portability 不変条件)として本ツールに同居させ、
verify には統合しない。

- gen / accept = 配布状態の変更
- verify = 同一性
- lint = 配布可能性

の三分類が最も一貫する。
