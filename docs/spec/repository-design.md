# リポジトリ設計

このリポジトリの設計上の決定事項を記す。実装の手順や順序は実装計画側の管轄であり、
ここには「何を作るか・何を不変条件とするか」だけを置く。

## 目的と責務境界

本リポジトリは、スキルリポジトリ向けの共有参照文書 vendoring ツールを提供する。
ツールの責務は次の2点のみとする。

- **配布**: 正本の共有文書を各スキルの配下へ決定論的に生成・展開する
- **同一性保証**: 配布先コピーが正本とバイト同一であることを digest で証明し、
  未承認の drift を検出する

互換性判定・退行検知は責務に含めない。digest が証明できるのは決定論的生成の
同一性のみであり、そこから「新しい版が既存スキルと互換である」ことは導出できない。
証明できないことをツールに保証させない。互換性の判定は消費側リポジトリの
regression 機構の責務とする。

ただしこの責務二分が成立するためには、採用の瞬間に互換性の証拠を束縛できる
結合点が必要である。gen は採用時に旧・新両方の digest を報告し、同じ値は lock の
git 差分にも必ず現れるため、消費側の regression 機構はその値に証跡を
突き合わせられる。pass/fail だけの記録では「別の版間で成功した証跡を根拠に
第三の版を採用する」取り違えを防げない。

## 宣言と pin の分離

スキル側の宣言は SKILL.md frontmatter に契約 id のみを書く。digest は書かない。
digest pin は中央の lock ファイルに置く。

宣言は「安定した依存の意図」、pin は「現在の採用内容」であり責務が別である。
id-only 化により、契約更新時に参照スキルの SKILL.md に diff が発生せず、
スキル読込のたびに消費される無関係トークンも消える。

## lock ファイルの正規形

lock は次の2区分を論理分離した正規形とする。

- dependencies: スキル → 契約 id 列
- resolutions: 契約 id → digest(および conformance digest)

混在させると「依存追加」と「契約更新」が同種の diff に見えるため分離する。
version フィールドは削除する(互換性判定には未使用の表示専用文字列であり、
未公開の現在なら削除は破壊的変更にならない)。ファイル名と JSON schema の
細部は実装計画で確定する。

同一 id の意味再利用はツールには判定できないが、採用履歴を消してはならない。
lock の git 履歴がその最低線である。

### 正本が消えた契約の resolution

正本は配布と台帳の基準である。正本の状態が変わり、宣言もそれを追認した
(スキルの宣言と正典ファイルの両方から消えた)契約は、gen が配布状態を
整合させるときに resolution も正規形から除去される。除去は静かに行われず、
その事実は出力に `retired: <contract-id>` として報告されるため、git の diff で
確認できる。

宣言が残ったまま正本だけが消えた場合は gen が closure として停止し、resolution は
保全される。つまり resolution が失われるのは宣言の削除を伴う意図的な撤退に
限られる。

宣言が消えても正本が残っている契約の resolution は lock に残り、gen が本文 digest と
conformance digest を更新し続ける。lock は正本から書き直す導出物であり、正本がある
限りその契約を記録する経路は gen だからである。

manifest は lock のみを持つ。ツールの版・出所・正本パスといったメタデータは
記録しない。検証のどの判断にも使われない値であり、特にツール自身の版をバイト比較
対象に含めると、ツールの版更新だけで全消費リポジトリの verify が落ちる。将来
manifest の形式や digest 規則を覆す変更が必要になったときは、その breaking release
が形式マーカーを導入し、欄の欠落自体を旧形式の印として扱う(先回りの版記録は、
比較から除外した瞬間に検証されない自己申告になるため持たない)。

## 採用 — gen への一本化

正本が権威であり、lock は gen が正本に合わせて書き直す導出スナップショットである
(package.json と lockfile の関係と同じ)。専用の承認コマンドは設けない。正本・lock・
配布コピーは同一リポジトリの同一 PR でレビューされるため、独立した承認境界は
同じ変更者による二重署名にしかならず、儀式化の温床になる。門番は PR レビューである。

- gen は契約の中身を切り替えたとき `adopted: <契約id> <旧digest> -> <新digest>` を
  出力に報告する(retired と同じ流儀)。lock に無かった契約の初回記録は
  `adopted: <契約id> <digest> (initial adoption)` として新しい値だけを名指す。門番では
  なく PR に貼れる変更サマリーであり、消費側の regression 機構が旧・新 digest に証跡を
  突き合わせる結合点でもある
- conformance ツリーの digest も同じ流儀で、本文 digest とは独立した 1 行として報告する
  (`adopted: <契約id> conformance <旧> -> <新>`、初回は (initial adoption)、テストが
  失われた場合は `retired: <契約id> conformance <旧>`)。本文と conformance は独立に
  動くため 1 行にまとめない
- CI は gen を実行しない。CI の役割は「ツリーが lock と食い違っている」ことの
  検出と fail のみ

## 検証の仕組み

verify は次の独立した照合を行う。どれか一つが失敗しても他の照合は意味を保つ。

- **正本 対 lock**: 宣言または lock が名指す各契約について、正本の digest が lock に
  控えた digest と一致するか(gen が lock を書き直す範囲と同一)。正本を変えたのに gen を
  実行し忘れたツリーはここで落ちる。宣言だけが残って正本が消えた契約は closure として
  報告し、宣言にも lock にも現れない contracts/ 配下の文書は照合の対象外とする
- **配布コピー 対 lock**: 各スキル配下のコピーが、lock の digest から再構築した
  期待バイト列と一致するか。コピーの手編集・欠落・余剰はここで落ちる
- **manifest の正規形**: vendor-manifest.json が、宣言・lock・正本の在否から機械的に
  書き直した場合の内容とバイト一致するか。正本が消えた契約の resolution は書き直しで
  落ちるため、その状態もここで落ちる
- **conformance 対 lock**: 契約に付属する conformance ツリーが、採用時に控えた
  digest と一致するか

manifest にツールの版を含む可変なメタデータは存在しないため、ツール自身の更新は
どの照合にも影響しない。digest の算出規則や manifest の形式を変える変更は、
それ自体が上記の照合を落とす(fail-closed)。

## vendored copy のヘッダ

生成物には編集禁止の表示(DO NOT EDIT と生成ツール名)・契約 id・正本 digest を付す。
契約本文を読むとき1回だけの消費であり、機械検証専用データを SKILL.md から追い出して
生成物側に置く情報配置である。

ヘッダは同一性保証にもセキュリティにも寄与しない。同一性は lock と verify の
バイト比較だけが担い、verify は埋め込まれた digest を入力として読まない
(lock から期待バイト列を再構築して照合する)。本文を改竄できる者はヘッダも
書き換えられる。ヘッダの根拠は次の2つである。

- 編集先の向け直し: 事情を知らない編集者に「これは生成されたコピーで、正本は別にある」
  と編集の時点で伝え、編集先を正本へ向け直させる。verify の検出は編集作業が済んだ
  後にしか働かないため、この機能は検出では代替できない。禁止の強制ではなく判断材料の
  提供であり、従う保証はない。強制は verify の役割である
- 正本の判別: ヘッダが無ければコピーは正本本文とバイト同一になり、検索で同時に
  見つかる同一ファイル群のどれが正本かを、ファイルの中身だけから判別する手段が消える。
  パス規約による判別は規約を知る者にしか働かず、スキルが単体で持ち出された後には
  残らない

digest 行はどの検証経路の入力でもないが、lock を伴わず持ち出されたコピーに残る
唯一の版の記録である。ヘッダを付す以上その限界コストは無視できるため、削らずに残す。

## 実装言語と配布

実装は TypeScript とする。実行時 API は特定ランタイムの独自 API(`Deno.*` 等)を
使わず、Node 互換の builtin(`node:fs`・`node:path` 等)と Web 標準 API
(Web Crypto 等)のみで書く。これにより Node / Bun / Deno のいずれでも動作し、
実装側の選好が利用側のランタイム要求に漏れない。

開発ツールチェーンは Bun(実行・テスト・パッケージ管理・publish)。ソースは
責務ごとのモジュール(src/)に分割し、テストは各モジュールに隣接して置く
(`src/{name}.ts` + `src/{name}.test.ts`)。CLI の入口はルーティングに徹し、
ロジックを持たない。

配布は npm レジストリを正本とする。package.json に bin を定義し、publish 時に
Node 互換 JS をビルドして同梱する(生成物はリポジトリにコミットしない。npm 配布の
標準慣行)。利用側は npx / pnpm dlx / yarn dlx / bunx で実行でき、Deno からも
`npm:` specifier で呼べる。利用側リポジトリにツールのソースを取り込む要求はない。

ツールは self-test コマンドを提供する。位置づけは実行環境で正しく動くことの
スモークチェックであり、実行するかは利用側の任意である。

依存は最小に保つが、確立した形式の解析は自作しない。frontmatter の YAML 解析と
.gitignore 規則の照合はエコシステムの実装を採用し、その上の検証層(宣言スキーマの
強制)だけを自前で持つ。手書きの制限文法パーサは「読めない入力を黙って空として
受理する」欠陥クラスを自ら再発明することが実測で示されたため採らない。

## セキュリティ不変条件

実装は次の不変条件を常に満たす。

- symlink による走査境界の逸脱を拒否する
- 期待する種別と異なるファイルシステム上の実体(ディレクトリの位置にファイル、
  通常ファイルの位置にディレクトリや FIFO 等)を、読み書きどちらの側でも
  「不在」や既定値として黙って扱わず、拒否して止まる
- 生成物の書き込みは原子的に行う
- 同一性検証はバイトレベルの走査で行う

(これらを TDD で先行して固める進め方や、agentic-meta で試作された旧 Python 実装の
テスト群を互換性契約ではなく境界条件チェックリストとして参照する規律は、
実装計画側で扱う。)

## 安定保証面(外部互換性)

verify がバイト同一比較である以上、次はすべて外部互換性そのものであり、
安定保証面として扱う。

- CLI・manifest schema・exit code
- digest アルゴリズム・正規化規則
- conformance ツリーの framing 規則
- vendor ヘッダのバイト形式
- violation kind
- gen の報告行(adopted / retired)の形式

Python API / TypeScript API の公開は、要求が観測されるまで行わない。

## 抽出境界

| 本リポジトリ | agentic-meta に残留 |
|---|---|
| ツール本体 | 契約の実内容 |
| ツールのテスト | skillset-alpha / beta(meta 側の合格条件測定器) |
| ツール検証 fixture(contracts-basic 相当) | 消費側 CI 配線 |
| 仕様文書 | 取り込んだツールの pin と出所記録 |
| ツール自身の CI | |

contracts-basic はツールの状態遷移を検査する fixture であり、ツール側の関心である。

## lint-selfcontain の位置づけ

スキルディレクトリの自己完結性検査(lint-selfcontain)は「配布」でも
「同一性保証」でもない第3の責務(portability 不変条件)として本ツールに同居させ、
verify には統合しない。

- gen = 配布状態の変更
- verify = 同一性
- lint = 配布可能性

の三分類が最も一貫する。
