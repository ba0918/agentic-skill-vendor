# 生バイト契約(ファイルとディレクトリの配布)

本ツールはこれまで、契約(スキルへ配布する共有物)を 1 つの Markdown 文書に限ってきた。
本章は、任意の数のファイルとディレクトリを、正本から各スキル内の指定位置へ生バイトの
まま配布する「生バイト契約」を定義する。動機は、複数のスキルが同じスクリプト群(例:
ワークフローのランタイム)を `scripts/` 配下に持つとき、共有文書と同じ問題 — 手動コピー
による正本の複製と、コピー同士のずれを検出する手段の不在 — が起きることである。加えて、
1 スキルの `scripts/` の中では責務で分解しづらく、単一の巨大なスクリプトが量産される。
正本を 1 か所に置き、そこで普通に分解したうえで、各スキルへ配布する。

生バイト契約は責務を広げない。配布と同一性保証の対象が「1 つの文書」から「ファイルの
集合」へ広がるだけであり、集合の digest・取得・リンク拒否は、conformance ツリーのために
既に存在する機構を使う。中身がスクリプトであることにツールは関知せず、実行もしない
(conformance script を実行しないのと同じ)。

用語。本章で「宣言」は SKILL.md frontmatter の契約 id の列を指し、`vendor-manifest.yaml` は
「表」と呼ぶ。既存の章が `vendor-manifest.yaml` を「宣言ファイル」と呼ぶ箇所は、本章の
確定時に「表」へ揃える。「配置」は、あるスキルのある dest にツールが何を書いたかの記録を
指す。path の「同一・配下・祖先」の判定は、本章のどこでも、末尾の `/` を 1 つ剥がした
文字列について、同一は等しいこと、配下は `<上>/` で始まること、祖先はその逆、と定める
(`scripts/rt` は `scripts/rt-old` の祖先ではない)。

## 設計の中心 — 配置先はスキルの自由、所有は lock が dest ごとに覚える

文書契約のコピーは `references/vendor/` というツール専有のディレクトリに落ちる。掃除も
衝突検出も、そのディレクトリを列挙すれば済む。生バイト契約は配置先を利用者が決めるので
その容器が無い。代わりに、**どのスキルのどの位置に何を書いたか**を lock が dest ごとに
覚え、gen と verify はその記憶を読んで動く。本章の全規則はこの 5 つの決定の上に立つ。

1. 配置の記録は dest ごとに、契約 id・src・配置の digest を持つ。契約の digest(正本の
   同一性)と配置の digest(その dest に在るべきもの)は別の値である
2. 配置の記録は gen だけが書き、他のコマンドは lock の値をそのまま持ち越す。表との
   食い違いは、lock の正規形照合ではなく、専用の照合(配置 対 表)が報告する
3. gen は生バイト契約について「コピー → 掃除 → lock」の順で書く。lock が配置を忘れる
   のは、その dest の掃除が済んだ後である
4. 一時ファイルはスキルの中に作らない。ツール専有の `.agentic-skill-vendor/` 配下で組み
   立ててから rename で正位置へ置く
5. ignore 規則は「配布するものが dest で ignore される」状態を拒否に変える。食い違いの
   状態を持ち越さない

## 表 — src と dest

生バイト契約は表の contracts の行に `files` を書いて定義する。`files` は正本の位置(src)
から各スキル内の配置先(dest)への対応であり、末尾が `/` の項目はディレクトリ丸ごと、
それ以外は 1 ファイルを指す。1 行の中で両者を混ぜてよい。

```yaml
contracts:
  workflow-runtime:                       # ディレクトリ丸ごと
    source: local
    files:
      tools/workflow-runtime/: scripts/_runtime/
  helper-scripts:                         # 任意の数のファイル
    source: workflow                      # リモート source でも同じ
    files:
      tools/scripts/run.py:  scripts/run.py
      tools/scripts/lint.sh: scripts/lint.sh
  changelog-entry:                        # 従来の文書契約。行の形は変わらない
    source: local
```

`files` を持たない行は従来の文書契約(Markdown ヘッダ付き・CRLF 正規化あり)であり、
既存の表は 1 バイトも変わらない。文書契約の配置先は従来どおり `references/vendor/<id>.md`
に固定する。配置先の自由が要るのはスクリプト等の生バイト側だけであり、動かしたい需要が
観測されてから広げる。

`files` は 1 件以上の対応を持たなければ拒否する(exit 2、空集合の契約は定義しない)。
`files` と `path` を同じ行に書いたら拒否する(exit 2)。現行の表は未知の鍵を黙って読み
飛ばすため、この拒否は新設であり、表の読み取り結果(`ContractOrigin`)が `files` を持つ
ことが実装の前提になる。`files` を持つ表を本章以前の版のツールが読むと、文書契約として
規約位置 `contracts/<id>.md` を探して closure で止まる。新しい表を古いツールで読む組み
合わせは支持しない。

### 配布集合の `ignore`

ディレクトリ src は、正本ではテスト・一時ファイル・開発用資料を実行時のファイルと
同居させることがある。ディレクトリを丸ごと配布すると、それらも各スキルへ届く。
このため表は、追跡済みの正本から配布するファイルだけを除外方式で選ぶ `ignore` を持てる。

表の最上位に書く `ignore` は、すべての生バイト契約のディレクトリ src に適用する。
各契約の行に書く `ignore` は、その契約だけへ追加適用する。設定は
`vendor-manifest.yaml` の 1 ファイルに集約し、別の ignore ファイルは設けない。

```yaml
ignore:
  - "**/*_test.py"
  - "**/*.tmp"

contracts:
  workflow-runtime:
    source: local
    ignore:
      - "fixtures/"
    files:
      tools/workflow-runtime/: scripts/_runtime/
```

`ignore` は省略可能な文字列の列であり、省略時は空とする。共通規則と契約固有規則は
除外を追加するだけである。`.gitignore` のパターン規則 — `*`、`**`、`/` による
位置指定、コメント、エスケープ — を使うが、除外済みファイルを再び含める否定規則
`!` は設けない。エスケープされていない `!` で始まる規則は、黙って無視せず表の
設定エラーとして拒否する。

各パターンの基準位置は設定ファイルの位置ではなく、展開するディレクトリ src の直下
である。同じ契約が複数のディレクトリ src を持つ場合、同じ共通規則と契約固有規則を
それぞれの src へ適用する。

配布用 `ignore` はディレクトリ src の展開だけに適用する。表が 1 ファイルを src として
明示した対応には適用しない。ファイル src はその 1 件を配る明示指定であり、共通規則で
暗黙に取り消さない。文書契約にも適用しない。

配布用 `ignore` とリポジトリの `.gitignore` は役割が違う。`.gitignore` は Git が
追跡する集合を決める。配布用 `ignore` は、その追跡済み正本から各スキルへ配る集合を
さらに狭める。ローカルのディレクトリ src では、両方の規則を通過した通常ファイルだけが
配布集合になる。リモート src では、取得元 commit が追跡する集合をキャッシュへ置いた後、
配布用 `ignore` だけで配布集合を狭める。

除外は配布集合を狭めるが、正本を検査する範囲を狭めない。リンク、src 内の
`.gitignore`、直下の `.vendored`、通常ファイル以外の実体など、既存の拒否条件は
除外前に検査する。危険または再現不能な入力を `ignore` で隠すことはできない。

1 つのパターンもファイルに一致しないことは正常である。共通規則が、ある契約には
該当しないことが普通にあるためである。一方、リポジトリの `.gitignore` を通過した通常
ファイルが 1 件以上あり、配布用 `ignore` を適用した結果 0 件になれば設定エラーとして
拒否する。gen はコピー・掃除・lock 書き換えより前に停止し、既存の配布物を変更しない。
verify も同じ設定エラーを返す。空のディレクトリエントリが残るかではなく、配布可能な
ファイル数で判定する。

### 宣言は id だけ、配置は契約ごと

スキル側の宣言は従来どおり id だけを書く。

```yaml
metadata:
  contracts:
    - workflow-runtime
    - helper-scripts
```

配置先をスキル側に書かないのは、宣言を id に限る既存の原則(docs/spec/repository-design.md
「宣言と pin の分離」)をそのまま守るためである。配置先は契約ごとに 1 つであり、スキル
ごとには変えない。別の位置に置きたいスキルがあるなら、同じ src を指す別 id の行を表に
もう 1 行書く。上書き機構は設けない。

### 導出しない、書記も触らない

生バイト契約の行は常に人間が書く。文書契約の行は規約位置 `contracts/<id>.md` の探索から
導出されるが、ファイルの集合にその規約位置は無い。したがって生バイト契約を 1 つでも
使う木は表を持つ。

表の書記(gen が行を書き足し、宣言されなくなった id の行を取り除く機構)は `files` を持つ
行を読み飛ばす — 取り除かず、`unmapped` も出さない。取り除くと、人が書いた src→dest の
対応を gen が黙って消し、復元できるのは人だけになる。宣言されなくなった生バイト契約の
行は、掃除の報告(後述)を見た人が取り除く。行が残っている間は、宣言が無いだけの契約
として lock に resolution を持ち続ける(文書契約で「宣言が消えても正本が残る」場合と同じ)。

### 契約の種類は lock が覚える

生バイト契約の resolution は `"kind": "raw"` を持つ(後述)。表に行が在る id について、
行の種類(`files` の有無)と lock の resolution の種類が食い違えば、gen も verify も拒否する
(exit 2)。生バイト → 文書、文書 → 生バイトのどちらの向きも同じである。契約の種類が黙って
変わると、一方の配布物が他方の掃除に拾われずに残る。表に行が無い id はこの検査に掛けない
(その状態は closure が扱う)。検査は書記が改訂した後の表 — gen が実際に動く表 — に掛ける。
宣言済みで規約位置に文書が在る id へ書記が `source: local` の行を足したとき、lock の
resolution が raw なら、それもこの検査で止まる。

種類を変える手順は 4 段である: 全スキルから宣言を外して gen(配置が掃除される)→ 行を
消して gen(正本を持たない契約として resolution が `retired` で落ちる。生バイト契約の行は
書記が消さないため、人が消す)→ 新しい種類の行を書く → 宣言を戻して gen。

`files` の行を、宣言が残ったまま人が消した場合は、その id は規約位置に正本を持たない
文書契約として読まれ、closure(exit 1)で止まる。そこから先は従来の closure の回復と同じ
(行を戻すか宣言を消す)。

### add と update

`add` の対応付けの規則は変えない。`add` が対応付けるのは規約位置で見つかった宣言済み
契約だけであり、生バイト契約はその探索に最初から掛からない。手順は「`add` で source を
登録 → `files` の行を書く → `fetch` → `gen`」であり、規約位置に無い文書契約(`path` を
明示した行)と同じ経路である。`fetch` は表が指す src を pin 済みの commit の列挙から
取るため、行を書いた後に `update` で pin を動かす必要はない。

`add` と `update`(`add` は `update` を呼ぶ)の報告に 1 行を足す。宣言済みで、表に行が無く、
ローカルの規約位置にも登録済みのどの source の規約位置にも無い id を、
`unlocated: <id> (no canonical text at any conventional location)` として名指す。報告行で
あり違反ではないので exit code は変えず、対処の文言も付けない(既存の報告行の形に揃える)。
表が 1 行も変わらない run でも出す — 現行は表が変わらない run の報告を捨てるため、報告の
受け渡しが実装の変更点になる。

`update` と `add` は lock を書くが、配置の記録は lock の値をそのまま持ち越す。掃除無しに
配置を書き換えてよいコマンドは無い。

### src の検査

src の鍵は末尾の `/` を 1 つ剥がした形で、文書契約の local path と同じ形の検査を通す
(空セグメント・`.`・`..`・バックスラッシュを含まない)。local の src はこのリポジトリ内の
通常ファイル(ファイル src)または通常ディレクトリ(ディレクトリ src)のみで、`skills/`
配下と `.agentic-skill-vendor/` 配下は指せない。理由は文書契約と同じである — スキル内を
正本にするとスキル間の暗黙依存が生まれ、キャッシュを正本にすると使い捨ての取得物が
配布の権威になる。この禁止は現行では `path` の読み取りに埋め込まれているため、`files` の
鍵にも掛けるには検査の切り出しが要る。

src が同じ source にある別の契約の conformance 位置
(`<正本の親>/<id>/conformance`)と同一・配下・祖先のいずれかなら拒否する。source が違えば
同じ文字列の path でも別の木なので衝突しない。conformance の収集は一つの source の中で
path の前方一致を使い、どの契約のものかを問わないため、祖先を許すと適合テストがスキルへ
配布され、配下を許すとスクリプトが適合テストとして pin される。

ディレクトリ src の「配下」は区切りを伴う前方一致で選ぶ。配下のファイルの dest は、src
からの相対 path を dest の下に付けたものである。

src の位置に立つものが期待する種別でない(ファイル src にディレクトリ、ディレクトリ src に
ファイル、どちらにもリンク等)場合は拒否して止まる(exit 2)。ディレクトリ src の内側の
リンクも拒否する。リンクの拒否は ignore 規則の適用より先に行う — 除外は digest する範囲を
狭めるのであって、見る範囲を狭めない(conformance ツリーと同じ順序)。

ディレクトリ src の直下に `.vendored` が在れば拒否する。正本の digest はそれを含み、
dest の digest は規則で除くため、gen が書いた木が決して verify を通らない。ディレクトリ
src のどこかに `.gitignore` が在れば拒否する。配布すれば消費側の作業木にその規則が立ち、
配布したファイル自身を git が追跡しなくなりうる(上流が `*.py` と書いていればランタイムが
コミットされない)。どちらの拒否も、local では gen と verify が正本を歩く時点、リモートでは
fetch が列挙を読む時点で行う(キャッシュにも置かない)。リモートの拒否は fetch の run 全体を
止める(取得は source ごとに丸ごと組み立ててから置くため)。抜ける手段は表の編集(その
ファイルを含まない src を指す)か上流の修正であり、拒否の文面はその 2 つを名指す。

不在は拒否ではなく、文書契約の正本が無いのと同じ closure(exit 1)である。1 つの契約の
src が複数あるとき、1 つでも不在なら closure とし、報告は不在の src を path 順に最初の
1 つから名指す。ディレクトリ src が在っても、リポジトリの `.gitignore` を適用した後に
ファイルを 1 つも持たないなら不在として扱う — git は空のディレクトリを持てず、チェック
アウトでは両者を区別できない。ファイル src がリポジトリの `.gitignore` の対象なら同じく
不在とする。配布用 `ignore` はファイル src に適用せず、ディレクトリ src を 0 件にした
場合は前述の設定エラーとする。

### dest の検査

dest は末尾の `/` を 1 つ剥がした形で、以下をすべて満たさなければ path を挙げて拒否する
(exit 2)。dest 単体の文字列だけで決まる検査は表を読む時点で、skill の宣言との組み合わせで
決まる衝突は gen と verify が最終配置を導出する時点で、木を見る必要がある検査(ignore、
位置に立つものの種別)は各コマンドが木を歩く時点で行う。表の読み取りは純粋な関数のまま
保つ。

- スキルディレクトリの内側に収まる相対パスである(空セグメント・`.`・`..`・
  バックスラッシュ・先頭の `/` を含まない)。lint-selfcontain が守る自己完結性を、
  配置の時点で守る
- `SKILL.md` ではなく、`references/vendor/` と同一・配下・祖先のいずれでもない。
  `references/vendor/` は文書契約の掃除が列挙する専有ディレクトリであり、2 つの所有規則が
  同じ位置を取り合ってはならない
- ファイル名が `.vendored` ではない。その名前はマーカーとして配置の digest から除かれる
  ため、そこに置いたファイルは verify できない
- src と dest の種別が一致する(末尾 `/` の有無が両側で揃う)
- 同じ skill の最終配置で、2 つの dest が同一・配下・祖先のいずれでもない。ディレクトリ
  dest は配下全体を所有するため、同じ skill では現在または将来のファイルが競合する。
  別 skill の配置は別のディレクトリに在るため、異なる契約が同じ dest 文字列を持ってよい。
  配置を行わない add、update、fetch は、この衝突を理由に拒否しない

同一・配下・祖先・予約位置の判定はすべて文字列の上で行う。大文字小文字や正規化形を
同一視するファイルシステムでは、文字列上は別で実体は同じ 2 つの位置を検出できない。
ディレクトリ dest ではその帰結は「検出できない」に留まらず、一方の配布が他方の配布した
バイトを消す。これは既知の限界であり、実体での判定は行わない(このツールは他のどこでも
文字列比較しか行わない)。同じ理由で、上流が大文字小文字だけ違う 2 ファイルを持つとき、
それを区別しない消費側では恒久的な drift になる。

ファイル dest の親ディレクトリはツールが専有しない。`scripts/run.py` を置くとき、
`scripts/` にスキル自身のファイルが在ってよい。ツールが専有するのは書いたファイルそのもの
と、ディレクトリ dest の中身全体だけである。

同じ dest の規則は、lock から読んだ配置にも課す。配置のスキル名は、ちょうど 1 セグメント
で、`.` でも `..` でもなく、`/` もバックスラッシュも含まない形でなければ拒否する(スキル
ディレクトリ名を検証する既存の規則は無い — 名前は readdir の結果であり、これまで path の
材料にならなかった。配置はそれを初めて削除先の材料にする)。lock の値は削除先を決める
入力であり、検査せずに読むと lock の 1 行の書き換えが削除先を変えられる。

形の検査が防ぐのは形の逸脱だけである。lock を編集できる者は、既存のディレクトリの配置の
digest を計算して、そのディレクトリを架空の契約の配置として書き足せる。その lock で gen を
走らせれば掃除がそれを消す。lock は PR レビューを通る内容であり、lock を編集できる者は
木も編集できるため、これは権限の昇格ではない。既知の限界として記す。

## digest — 契約の digest と配置の digest

framing は conformance ツリーと同じ形である。ファイルを path の code unit 順に並べ、
各ファイルを `相対パス NUL バイト長 NUL 内容` で framing し、全体を 1 つの digest にする。
内容は生バイトであり、文書契約の正規化(CRLF → LF)は掛けない。スクリプトは書かれた
バイト列のまま実行されるため、改行も pin の一部である。形を新設しないのは、framing が
安定保証面だからである。ただし path の基点は用途ごとに違い、同じ集合が 2 つの値を持つ。

- **契約の digest**(resolution に載る、正本の同一性): 契約が配る全ファイルを 1 つの
  集合とし、path は表の鍵に書かれた src の path(ツリー root 相対。ディレクトリ src は
  その配下へ展開)で framing する。dest に依存しない
- **配置の digest**(lock の配置に載る、その dest に在るべきもの): ディレクトリ dest は
  その配下のファイルを dest からの相対 path で、ファイル dest はその 1 ファイルをファイル名
  (最後のセグメント)で framing する。どちらも dest の位置に依存しない

契約の digest が dest に依存しないため、表で dest だけを書き換えても `adopted` は出ない。
第 2 版までは「配置が変わったことを `adopted` で diff に出す」としていたが、撤回する。
配置の変化は lock の `placements` の diff と掃除の報告行に現れる。

裏返しに、契約の digest は src の配置(表の鍵)に依存する。正本を `tools/workflow-runtime/`
から `tools/rt/` へ動かすと、内容が同じでも digest が変わり `adopted` が出る。上流が
レイアウトを整理したときも同じである。文書契約(本文だけの digest)と違い、src の
並びは生バイト契約の同一性の一部である — 意図した非対称であり、この場合の `adopted` の
旧新 digest の差は、正本側の git diff ではなく表の鍵の差が示す。

ディレクトリ dest の直下に立つ `.vendored` は配置の digest から除く。それより深い位置の
`.vendored` は普通のファイルである。

ファイルの mode(実行ビット)は framing に含まれず、pin されず、gen も写さない。書き込みの
原始操作は mode を設定せず、配布されたファイルはツールの既定の mode で立つ。「実行ビットが
違えば別物」を保証したいなら framing の変更 — つまり breaking release — が要る。配布先の
スクリプトは `python path/to/script.py` のように解釈器経由で呼ぶ前提とする。手元で
`+x` 付きで持っていたスクリプトを生バイト契約へ移すと、この前提に合わせて呼び出し側を
書き換えることになる。

### リポジトリの `.gitignore` 規則

適用する規則は、local では消費側のツリー root からその位置の親までの `.gitignore`(木の
中の `.gitignore` だけを読む既存の機構のまま。グローバルの除外設定は読まない)、リモート
では無し(何を追跡するかは取得元が決めている)。src・dest の内側の `.gitignore` は数に
入らない(src の内側は拒否、dest の内側は配布されない)。

- local のディレクトリ src には適用する。チェックアウトに無いファイルを pin しない
- dest の位置そのもの、またはその祖先が ignore されていれば、gen と verify は木を歩く時点で
  拒否する(exit 2、規則の出所を挙げる)。ignore された dest は verify から見えず、gen と
  verify が「綺麗」と「違反」で食い違う状態に落ちる。ディレクトリ dest を判定するときは、
  その位置をディレクトリとして問う(`name/` の形の規則が当たる)。現行の判定は最後の
  セグメントを常にファイルとして問うため、種別を渡せる形への変更が実装の前提になる
- 配布するファイルのどれか、またはディレクトリ dest 直下の `.vendored` が dest の位置で
  ignore されるなら、gen は計画の時点で拒否する(exit 2、ファイルと規則の出所を挙げる)。
  この拒否により、dest 側で ignore 規則を適用した集合は常に配置の digest の集合と一致する。
  src 側と dest 側で規則の当たり方が違っても、食い違いは状態として残らず、その場で止まる
- ディレクトリ dest の中で ignore されるファイル(実行で生まれた `__pycache__/` 等)は、
  配置の digest に入らず、verify も数えず、ツールが所有する dest の置き換えで一緒に消える。
  ディレクトリ dest はツールの専有領域であり、ローカルの設定や秘密をその中に置く場所では
  ない。この受容は README にも書く(利用者が読む場所に置く)

### 選別の適用位置

fetch は配布用 `ignore` を適用しない。リモートのディレクトリ src が持つ全ファイルを
従来どおり取得・検品してキャッシュへ置く。これにより `ignore` の変更だけなら再取得せず、
同じキャッシュから新しい配布集合を作れる。

gen と verify は、ローカル正本またはリモートキャッシュを読む共通の境界で同じ選別を行う。
選別後のファイルだけを契約 digest、配置 digest、配布物へ含める。除外ファイルだけを
変更しても、この 2 つの digest と配布物は変わらない。

`ignore` の設定自体は lock に記録しない。lock が記録するのは、選別後に実際に採用した
ファイル集合の digest と配置である。パターンを変更しても選別結果が同じなら、lock は
変化しない。

以前は配布していたファイルが新しい `ignore` で配布集合から外れた場合、gen は次の実行で
そのコピーをディレクトリ dest から削除する。削除前に正本を読める verify は drift を
報告する。配布用 `ignore` は配布先の走査には適用しないため、利用者が配布先へ置いた
同名ファイルを検証から隠す規則にはならない。

リモート正本のキャッシュがない verify は、既存のリモート契約と同じく正本を必要とする
照合を省略し、現在の lock と配布物を照合する。この状態では `ignore` の変更後の集合を
再計算できないため、その変更だけを理由には失敗しない。完全な照合が必要な場合は fetch の
後に verify を実行する。gen は従来どおり、必要なキャッシュがなければ何も書かずに fetch を
指示して停止する。

## lock — 配置の記録

lock に `placements` 節が加わる。スキル → dest → {契約 id, src, 配置の digest}、であり、
生バイト契約を 1 つも配っていない木では節ごと現れない(`sources` 節と同じ)。gen は配置を
持たないスキルを鍵ごと落とした形で書く。生バイト契約の resolution は `"kind": "raw"` を持ち、文書契約の
resolution は従来の形のままである。

```json
{
  "dependencies": { "skill-a": ["changelog-entry", "workflow-runtime"] },
  "placements": {
    "skill-a": {
      "scripts/_runtime/": {
        "contract": "workflow-runtime",
        "digest": "sha256:...",
        "src": "tools/workflow-runtime/"
      }
    }
  },
  "resolutions": { "changelog-entry":  { "digest": "sha256:..." },
                   "workflow-runtime": { "digest": "sha256:...", "kind": "raw" } },
  "sources": { ... }
}
```

- `placements` は gen だけが書く。期待 lock の描画(verify、update、add が使う)は、節を
  鍵ごと無条件に lock から持ち越す — `dependencies` に無いスキルの鍵も、表に無い契約の
  配置も落とさない。resolution や sources が「値は持ち越し、項目は剪定」なのと違い、この
  節は項目も剪定しない。剪定すると、最後の宣言を外したスキルの配置が `update` 1 回で
  掃除の前に消え、その dest は誰も覚えていない孤児になる。帰結として、宣言を外してから
  gen するまでの間、verify は `placement` を報告し続ける。「配置を持たないスキルは鍵ごと
  落とす」は gen が書くときの形であって、描画の剪定規則ではない
- 導出で描画しないのは、1 契約が 1 スキルに複数の dest を持つとき、持ち越す digest を
  どの鍵に付けるかが決まらず、dest を書き換えて `update` を打っただけで掃除無しに鍵が
  付け替わるからである
- 表との食い違いは、lock の正規形照合では見えない(持ち越した値は自分自身と比べられる)。
  専用の照合「配置 対 表」を verify に足す(後述)
- 鍵はすべて code unit 順(lock の正規形と同じ `compareStrings`)に描画し、ディレクトリ
  dest と src は末尾の `/` を保つ
- 記録をスキル × dest で持つのは、門がスキル × dest の事実だからである。契約ごとに持つと、
  スキル A が `scripts/_runtime/` を記録した時点でスキル B の同じ位置も「記録済み」に見え、
  B にだけ在った利用者のファイルが置き換えで消える
- src を持つのは、同じファイル名の dest を入れ替える編集を検出するためである。配置の
  digest はファイル名で framing するため、`tools/a/run.py → scripts/x/run.py` と
  `tools/b/run.py → scripts/y/run.py` の入れ替えでは digest も鍵も変わらない。src の列だけが
  違う
- 生バイト契約を使わない木の lock はバイト単位で従来と同一である。表を持たない木は
  fixture の contracts-basic が、表を持つが生バイト契約の無い木は contracts-remote が、
  その確認である

「正本が在る」(lock が resolution を保つ条件)は、local の生バイト契約では「全 src が
在る」と読む。文書契約の「通常ファイルが在る」をそのまま当てると、ディレクトリ src は
常に不在と判定され、gen のたびに resolution が落ちる。リモート契約は従来どおり、表に
行が在ることをもって在るとする — クリーンチェックアウトはキャッシュを持たない。

## 配布 — ツールは自分が書いたバイトしか消さない

gen は各 dest を正本とバイト同一にする。ディレクトリ dest では、正本に無いファイルが
dest に在れば消すことを含む。残すと「古いファイルが残ったまま verify が通る」穴になる。

### 門 — 書いてよい dest

gen は計画の時点で、書く dest ごとに次を 1 → 2 → 3 の順に確かめ、最初に満たした条件で
扱う。1 つでも満たさない dest があれば、何も書かずに path を挙げて拒否する(exit 2)。

1. dest が不在である
2. lock の `placements` がそのスキルのその path に配置を持ち(種別が今と違っていても
   よい)、dest の現在の中身がその配置の digest と一致する
3. dest の現在の中身がこの run が書くものと一致し、かつ ignore 対象を含めて、書くもの
   以外のファイルを 1 つも持たない。この条件で扱った dest は
   `claimed: skills/<skill>/<dest> (<id>)` で報告する

1 が、書き間違えた dest に利用者のファイルが在る場合を止める。2 が、前回の gen の後に
利用者が dest の中へ足した(ignore されない)ファイルを無言で消す経路を止める。ディレクトリ
の置き換えは利用者のファイルを巻き込めるため、文書契約のコピー(1 ファイルをツールが
上書きする)より厳しく扱う。3 が回復経路である — lock を失った木、コピーを書いた直後に
止まった run の後、手でコピーしてあった移行前のディレクトリ、どれもこの条件で取り込み、
lock が記録し直される。

条件 2 と 3 の「中身」は配置の digest と同じ見方で取る — ディレクトリ dest は ignore 後の
集合を dest 相対で、ファイル dest はその 1 ファイルをファイル名で framing したもの。条件 2 は
**lock の配置が覚える種別**で取り、条件 3 はこの run が書く種別で取る。木に立つ実体の種別が
lock の配置の種別と違えば(lock はディレクトリと覚えているのにファイルが立つ等)、条件 2 は
計算できず、その dest は拒否される。種別の切り替えとは、lock と木の種別が一致し、表だけが
新しい種別を求める状態を指す。
条件 2 の下では、ディレクトリ dest 内の ignore 対象は digest に入らず、置き換えで消える
(ツールが所有する領域の副産物として扱う)。条件 3 は ignore 対象まで空であることを求める —
取り込みはまだツールのものでないディレクトリを置き換える行為であり、`.env` のような
ローカルファイルが残っていれば、取り込まずにそのファイルを名指して止まる。`__pycache__/`
のような実行の副産物も同じ扱いになる。ツールには両者を区別できないため、回復の手順は
「名指されたファイルを消して gen をやり直す」である。この非対称 — 所有後は副産物を黙って
消し、取り込み時は名指して止まる — は、所有の境界をまたぐ瞬間にだけ人の判断を挟む、
という意図である。

### 掃除 — 消してよい dest

掃除の対象は、lock の `placements` に載っている(スキル, dest)の組のうち、この run が
書く(スキル, dest)の組と同一でないものである。比較は組で行い、dest の文字列だけでは
行わない — スキル A と B が同じ `scripts/rt/` を持ち A が宣言をやめたとき、B の dest を
書くことが A の掃除を免除してはならない。「スキルが宣言をやめた契約の dest」「表で dest が書き換えられた契約の旧
dest」「名前を変えたスキルの旧 dest」「表から行が消えた契約の dest」がここに入る。

書く dest と lock の配置が同一でなく、同じ skill 内で入れ子(配下・祖先)になる組み合わせは、
後述の所有権移行として計画する。安全条件を満たさない組み合わせは計画の時点で拒否する
(exit 2)。別 skill の配置は木の別の位置に在り、所有権移行にも衝突にもならない。

消してよいのは、dest が不在(消す仕事が無い — 消えていることが求めた状態である。スキルの
ディレクトリごと消えた場合を含む)か、現在の中身がその配置の digest と一致する dest だけ
である。この判定も計画の時点で行い、一致しない dest があれば何も書かずに拒否する(exit 2、
食い違うファイルを path 付きで)。宣言をやめた後でディレクトリを自分のものとして編集し
始めた利用者の作業を、撤退の掃除が消さないためである。

掃除した dest は `cleared: skills/<skill>/<dest> (<id>)` で、不在だった dest は
`cleared: skills/<skill>/<dest> (<id>; already absent)` で報告する。後者が無いと、スキル
ディレクトリごと消えた・改名されたときに、配置が落ちた事実が出力のどこにも残らない。契約が全
宣言から外れて表の行も消え、resolution が落ちるときは、既存の `retired: <id>` がそれに
加わる。報告行に載せるスキル名と dest は、既存の違反行と同じく `displayName` を通す
(木が供給する名前は制御文字を含みうる)。

### 重なる配置の所有権移行

lock が記録する旧配置と、この run が書く新配置が同じ skill 内で重なる場合、その組を
所有権移行として扱う。移行対象だけが所有する最外周の旧または新 dest を、一括置換の単位と
する。単なる共通の親ディレクトリは置換単位にしない。その親に無関係な契約や利用者の内容が
在る可能性まで、移行を理由にツールの所有物として扱わないためである。

旧配置がすべて lock の配置 digest と一致し、新たに所有する範囲に旧配置が所有していない
内容が無ければ、最終内容を staging で組み立て、最外周 dest を 1 回置き換える。旧
ディレクトリから配下の複数ファイルへ分ける場合、複数ファイルから親ディレクトリへまとめる
場合を含め、ファイル・ディレクトリや親子関係の向きは問わない。

旧配置が変更されている、新たに所有する範囲に利用者の内容が在る、または移行対象だけを
一括置換できない場合は、何も書かずに拒否する。旧ディレクトリの配置 digest はファイル単位の
履歴を持たないため、食い違う木から旧生成物だけを選んで消すことはできない。移行対象の
最外周 dest の外は検査・変更しない。

一括置換は既存のディレクトリ dest の置き換えと同じく、削除と rename の間の短い不在を
許容する。再実行時に最外周 dest が旧状態、不在、または完成状態なら、最終配置と lock へ
収束する。それ以外の部分状態や利用者変更は拒否する。新しい lock 項目や恒久的な復旧
ファイルは追加しない。追加の走査とコピーは移行対象のファイル数と総バイト数に比例し、
ネットワーク通信や外部プロセスを増やさない。

完成状態は、各ディレクトリ dest の `.vendored` を含む予定ファイル集合と、ignore 対象も
含めて最外周 dest に実在する全ファイル集合の path・種別・バイトが完全に一致する状態だけを
指す。余分・欠落・改変のどれかがあれば、旧配置の種別と digest を満たす旧状態として検査を
続け、そこも満たさなければ部分状態として全書き込み前に拒否する。

### 順序

生バイト契約についての書き込みの順序は「コピー → 掃除 → lock」である。文書契約の
「コピー → lock → 削除」と違うのは、生バイト契約では lock が dest の唯一の記憶だから
である。lock を先に書くと、掃除が 1 つ失敗した時点で、その dest を誰も覚えていない孤児に
なる。掃除を先に置いても失われるのは門が「ツールが書いたバイト」と確かめたものだけで、
正本から書き直せる。掃除の途中で失敗すれば、残りの掃除を試みてから lock を書かずに止まり
(既存の削除ループと同じく失敗を集めて報告する)、次の gen が同じ掃除をやり直す。

1 run の実際の順序は「全コピー → 生バイト契約の掃除 → lock → 文書契約の削除」である。
文書契約側の順序は変えない。

### 原子性

ファイル dest・ディレクトリ dest とも、ツール専有の `.agentic-skill-vendor/staging/` の下で
組み立ててから rename で正位置へ置く。スキルの中に一時名のファイルやディレクトリを作ら
ない。作ると、その一時名は門のどの条件にも掛からない利用者領域への書き込みになる(既存の
`<site>.tmp` はスキル領域の外 — `references/vendor/` の中か木の root — に作られる)。

rename が原子的なのは同一ファイルシステム内だけである(既存の一時名が兄弟に置かれている
理由と同じ)。`.agentic-skill-vendor/` と `skills/` が別のファイルシステムに在る木では、
旧 dest を消す前に staging と dest の親が同じデバイスに在ることを確かめ、違えば何も消さず
に拒否する(exit 2)。

staging はキャッシュと同じくコミットしない領域であり、run の開始時に前回の残骸を丸ごと
捨てる。捨てる前に、`.agentic-skill-vendor/` 自身とそこへ至る親の連なりにリンクが無いこと
を確かめる。現行のキャッシュの掃除は revision ディレクトリとその直近の親だけを見て、
`.agentic-skill-vendor/` 自身を見ない — 再帰削除の根がリンクなら削除は木の外へ届く。
この検査はキャッシュの掃除にも課し、remote-sources.md の「リンクを拒否する位置」に
`.agentic-skill-vendor/` 自身を加える。gen は `.agentic-skill-vendor/` が ignore されて
いなければ警告する。現行の警告はキャッシュディレクトリだけを問い、取得コマンドだけが
出すため、local の生バイト契約しか使わない木では一度も出ない。

保証は「dest 1 つは丸ごと在るか丸ごと無いかのどちらかで、半分だけ書かれたディレクトリは
存在しない」までである。既存のディレクトリ dest を置き換えるときは、旧 dest の削除と
rename の間に dest が不在の瞬間がある — rename は空でないディレクトリを置き換えられない。
止まった run は、旧 dest のまま・不在のどちらかを残し、不在は verify が drift として報告し、
次の gen は条件 1 で書き直す。この 1 点は repository-design.md の「生成物の書き込みは
原子的に行う」の緩和であり、確定時に同章へ書き足す。同章の不変条件が受容している「検査と
使用の間の入れ替え」は、新設の再帰削除(ディレクトリ dest の置き換えと掃除)にも同じ範囲で
及ぶ。

### dest の位置の検査

dest の位置に立つものが表の期待する種別でも不在でもない(ファイル dest にディレクトリ、
ディレクトリ dest にファイル、どちらにもリンク等)場合、gen はまず門の 3 条件を試し、どれも
満たさない dest にだけこの拒否を立てる(種別の切り替えは条件 2 で、切り替えの途中で止まった
run の後は条件 3 で通る)。verify は lock の配置の種別と木の種別が違えば拒否する。リンクは
どの場合も拒否する。dest に至る親の連なり(スキルディレクトリから dest まで)に立つリンクも、
読む側・書く側・消す側のすべてで拒否する。ディレクトリ dest の内側で見つかったリンクも
拒否する。

### マーカー

配布するファイルにはヘッダを付けない。文書契約のヘッダは Markdown の先頭に 4 行足す形で
あり、JSON・バイナリ・実行されるスクリプトには同じ形で入れられない。

ディレクトリ dest の直下には `.vendored` という 1 ファイルを置く。バイト列は文書契約の
ヘッダと同じ 4 行(末尾の空行を含む)であり、`source-digest` 行には**契約の digest**を
書く(1 つの契約が複数のディレクトリ dest を持てば、すべて同じバイト列になる)。根拠は
ヘッダと同じ 2 つ — 事情を知らない編集者への向け直しと、検索で同時に見つかる同一ファイル
群のどれが正本かの判別。抑止にはならず、同一性にも寄与せず、門でもない。verify はその
存在と内容を lock から再構築した期待バイト列と比べ、違えば drift として報告する。

ファイル dest にはマーカーを置かない。ファイルの隣に別ファイルを置けばそれは親
ディレクトリへの書き込みであり、ツールが専有しない場所へ物を足すことになる。

## 取得 — conformance ツリーと同じ経路

リモートの生バイト契約は、取得元 commit の木の列挙から `files` の各 src(ファイルなら
その 1 件、ディレクトリなら区切り付き前方一致の配下)を選び、conformance ツリーと同じ
経路で取得する。path の形の検査、blob object id による検品、revision ディレクトリ単位の
原子的配置、lock から参照が消えた revision の掃除は、既存の規則がそのまま掛かる。
1 ファイルあたりのバイト数の上限(既存の取得経路が持つ)も引き継ぐ。その拒否の文面は
「共有文書」を前提にしているため、生バイト契約を含む形に改める。ファイル数には上限を
設けない。転送はファイルごとの要求であり、ディレクトリ src はその数だけ要求を増やす。
「共有物は少数・小さい」という既存の規模前提を引き継ぐ。

mode を検査する位置は、取得する各ファイルと、ディレクトリ src が立つ位置そのものの
2 つである。前者は通常ファイル以外を拒否する(黙って落とすと「取得元が持っていない」と
「持つが取れない形で持っている」が区別できない)。後者はリンクとサブプロジェクトを
拒否する(その下が列挙に現れず、在るディレクトリが空として pin される)。conformance
ツリーの位置に課している検査と同じものである。

src が列挙に無ければ、文書契約のリモート正本が無いのと同じく、取得は何も書かずに
止まる(exit 2)。closure(exit 1)はローカル正本の不在を報告する違反であり、リモートには
従来から適用されない。この状態から抜ける手段は `update`(pin を動かす)か表の編集で
あり、拒否の文面はその 2 つを名指す(既存の文面はどちらも名指していないため、文面の
変更になる) — `fetch` を名指すと同じ状態へ戻るだけである。

gen と verify がキャッシュを要する条件も文書契約と同じである — リモートの生バイト契約は、
全 src がキャッシュに在るときだけ正本との照合に掛かり、無ければ gen は何も書かずに fetch を
指示して止まり(同じ run の他の掃除も走らない)、verify は正本を要する照合を黙って飛ばす。

### 実装が置き換える前提

現行の実装は「契約 = 1 つの正本ファイル」を `ContractLocation`(単一 `site`)で表し、次の
箇所がそれに乗っている。生バイト契約はこれらすべてに種類による分岐を要する。

- 表の行から正本の位置を決める箇所(`path` の無い行を規約位置 `contracts/<id>.md` へ
  落とす既定)。`files` の行はここを通らない
- 正本の読み取り(CRLF 正規化を伴う本文の読み取り。生バイトはそれを通らない)
- resolution の導出と conformance の探索(生バイト契約では探索しない)
- 「正本が在る」の判定、closure と stale-lock の判定、キャッシュ在否の判定
- 配布コピーの照合(文書契約は `references/vendor/<id>.md` を見に行く。生バイト契約は
  配置を見る)

## 報告・検証

- gen の報告は文書契約と同じ `adopted` / `retired` に、`claimed` と `cleared` が加わる。
  集合の中のどのファイルが変わったかは報告しない。lock の diff は digest 1 行であり、
  内容の差は正本側の git diff が示す
- 生バイト契約では conformance ツリーを探索しない。位置が無いからではなく、規則として
  探さない
- verify の照合は、文書契約の 4 種のうち conformance を除く 3 種に、**配置 対 表**を
  加えた 4 種である。配置 対 表は、宣言と表から導出した「各スキルが持つべき配置(dest →
  契約 id, src)」と lock の `placements` を比べ、違いを `placement` として報告する — 表で
  dest を書き換えて gen を忘れた木、同じファイル名の dest を入れ替えた木、`dependencies` に
  無いスキルの配置、はここで落ちる。表に行が無い宣言済み id からは配置を導出せず、その id
  の lock の配置は closure が報告している間 `placement` を出さない(1 つの欠落を 2 つの
  kind で言わない)。配布コピー対 lock は、各 dest から再計算した配置の digest と
  `.vendored` を lock の値と比べる。正本を必要としないため、リモート契約でもキャッシュ
  無しで完走する。歩く dest は lock の配置のうち、配置 対 表 が食い違いを報告しなかった
  (スキル, dest)の組である — 消えたスキルの配置を `placement` と `drift` の両方で言わない
- violation kind は既存のものに `placement` を加える。`extra` は使わない — その文面「どの
  宣言にも答えない」は専有ディレクトリの列挙を前提にしており、生バイト dest に列挙は無い

| 状態 | kind |
|---|---|
| dest の中身が配置の digest と違う(余分・欠落・改変を含む)。ファイル dest なら path を、ディレクトリ dest なら正本が手元に在れば食い違うファイルの path を、無ければ dest を名指す | drift |
| dest が不在 | drift |
| `.vendored` が不在、または内容が期待と違う | drift |
| lock の配置の digest を手で書き換えた | drift(持ち越した値は再計算した値と比べられる) |
| local の src が resolution と違う(正本を変えて gen を忘れた) | stale-lock(文面は契約 id と旧新 digest を名指し、src の path は挙げない — 既存の文面が置く 1 つの正本 path は複数 src では成り立たない) |
| 宣言された契約に resolution が無い | unresolved |
| 表の dest・src・契約と lock の配置が食い違う。配置があるのに宣言が無い | placement |
| lock の配置の鍵を手で書き換えた | placement |
| local の src が不在 | closure |
| 表の種類と resolution の種類が食い違う | 拒否(exit 2) |
| src・dest の位置に期待と違う種別が立つ、親の連なりにリンク | 拒否(exit 2) |

表にも lock にも無い位置に立つものは、どの照合にも掛からない。容器を持たない設計の帰結
であり、検出対象外である。

## 状態遷移

主な遷移と、その帰結。「配置」は lock の `placements`。

| 遷移 | 帰結 |
|---|---|
| 初回 gen、dest 不在 | 条件 1 で書く。配置を記録 |
| 初回 gen、dest に手コピーがあり余分が無い | 条件 3 で取り込む。`claimed` |
| 初回 gen、dest に手コピーがあり `.env` 等が残る | 拒否、そのファイルを名指す |
| 初回 gen、dest に無関係な利用者のファイル | 拒否 |
| 何も変えずに gen を 2 回 | 2 回目は全 dest が条件 2。`claimed` は出ない |
| 正本を編集 → gen | 条件 2 で置き換え。`adopted` |
| 正本を編集、gen 忘れ → verify | stale-lock(local)/ 静かに飛ばす(リモート、キャッシュ無し) |
| 宣言を足す、gen 忘れ → verify | placement(導出した配置に在り、lock に無い)。lock の配置しか歩かないため drift は出ない |
| dest の中を手で編集 → gen | 拒否、食い違うファイルを名指す。verify は drift |
| dest の中に ignore 対象が生まれる(`__pycache__/`)→ gen / verify | 条件 2 で置き換え、一緒に消える / 数えない |
| 2 スキルが共有、片方が宣言をやめる → gen | そのスキルのその dest を掃除。`cleared` |
| 2 スキルが共有、片方のスキルディレクトリを消す → gen / verify | 消えた側の dest は不在で掃除済み扱い(`cleared ... already absent`)。残る側はそのまま / `placement` と `lock`(dependencies が変わる)。drift は出ない |
| 全スキルが宣言をやめる(行は残る)→ gen | 全 dest を掃除。resolution は残る。人が行を消すと次の gen で `retired` |
| 行を消す、宣言は残る → gen | closure(exit 1) |
| 行を消し、宣言も無い → gen | `retired`。配置が残っていれば掃除 |
| 表で dest を改名 → gen | 新 dest を条件 1 で書き、旧 dest を掃除。`adopted` は出ない。配置が動く |
| 表で dest を改名、gen 忘れ → verify | placement |
| 表で同じファイル名の dest を入れ替え、gen 忘れ → verify | placement(src が違う) |
| 表で 2 契約の dest を入れ替え → gen | 両方とも条件 2(配置の digest は dest 側に付いている)で置き換え。掃除対象なし |
| 同じ契約の 2 dest を入れ替え → gen | 同上 |
| dest を入れ子に変更(`scripts/` → 配下の複数ファイル、またはその逆等)→ gen | 旧配置が lock と一致し、新規所有範囲に利用者の内容が無ければ、最外周 dest の所有権移行として 1 回で完了。安全条件を満たさなければ既存コピーと lock を変えずに拒否 |
| 同じ path で種別を切り替え → gen | 条件 2(種別違いを許す)で置き換え |
| 契約 id を改名(src・dest は同じ)→ gen | 条件 2 で置き換え(配置の digest は id に依存しない)。`retired` 旧 id、`adopted` 新 id。`.vendored` の id 行が変わる |
| 表の行を文書契約 ↔ 生バイト契約で書き換え → gen | resolution の種類と食い違うので拒否。全宣言を外して gen → 行を消して gen(`retired`)→ 新しい行 → 宣言を戻す、の 4 段 |
| スキルディレクトリを改名 → gen | 新名の dest を条件 3 で取り込み(`claimed`)、旧名の dest は不在で掃除済み扱い。dest に ignore 対象が残っていれば名指して拒否、消してやり直す |
| dest の祖先ディレクトリを手で改名 → gen | 宣言が残る限りその組は書く対象なので、条件 1 で書き直す。`cleared` は出ない。改名先のバイトはどの照合にも掛からない |
| lock を削除 → gen | 全 dest を条件 3 で取り込み(`claimed`)。文書契約と同じく記録し直し。dest に ignore 対象が残っていれば名指して拒否、消してやり直す |
| lock の配置の鍵を手で改変 → gen / verify | 形が壊れていれば拒否、書く dest と入れ子なら拒否、それ以外は掃除対象として吸収され `cleared ... already absent` / placement |
| lock の配置の digest を手で改変 → gen / verify | 条件 2 は落ち、中身が書くものと一致すれば条件 3 で `claimed` / drift |
| 配置はあるが resolution が無い契約 → verify | placement(表に無い)または unresolved |
| コピーの後・掃除の前で停止 → gen | 新 dest は条件 3(`claimed`)、掃除はやり直し |
| 掃除の途中で停止 → gen | lock は古いまま。掃除をやり直す(消えた dest は掃除済み扱い) |
| ディレクトリ置き換えの削除と rename の間で停止 → verify / gen | drift / 条件 1 で書き直し |
| staging と dest が別ファイルシステム | 何も消さずに拒否 |
| dest またはその祖先が ignore 対象 | 木を歩く時点で拒否 |
| 配布するファイルか `.vendored` が dest で ignore 対象 | 計画時に拒否 |
| 上流の src 内に `.gitignore` / `.vendored` | fetch で拒否、キャッシュに置かない。表の編集か上流の修正を指示 |
| リモートの生バイト契約でキャッシュ無し → gen | 何も書かずに fetch を指示(同じ run の掃除も走らない) |

## lint-selfcontain との関係

lint-selfcontain は配布されたファイルも従来どおり走査する。配布されたスクリプトが
絶対パスや `../` を含めば、それはスキルを単体で持ち出せない理由として正しく報告される。
正本側は走査しないため、1 か所の違反がスキル数ぶん報告される。local の正本なら直す場所は
1 か所である。リモートの正本なら消費側に直す手段も除外する手段も無く、上流の修正か
その契約の撤退しかない。

## 安定保証面の変更

本章が加えるものはすべて安定保証面であり、版を上げて出す。

- 表の schema: `files` 欄、`files` と `path` の併記の拒否
- 表の schema: 最上位と生バイト契約の行に置く省略可能な `ignore` 欄、および否定規則の拒否
- lock の schema: `placements` 節、resolution の `kind` 欄
- `.vendored` のバイト形式
- 報告行: `unlocated`(add / update)、`claimed`、`cleared`(gen)
- violation kind: `placement`
- 既存の文面の変更: リモート正本の不在(回復手段を名指す)、1 ファイルの上限(「共有文書」
  の語)
- digest: conformance の framing 形式を、契約の digest と配置の digest に(基点を変えて)
  適用すること
- digest: 生バイト契約の契約・配置 digest は、配布用 `ignore` 適用後の集合から計算すること
- ディレクトリ dest の置き換えにおける原子性の緩和

生バイト契約を使わない木の lock・gen・verify の出力はバイト単位で従来と同一である。
`unlocated` だけは生バイト契約を使わない木でも出うるが、報告行の追加であって既存行の
変更ではない。以上から minor version とする。

## 初期スコープと前提

- transitive 依存(配布したファイルがさらに別の契約を要求すること)は無い
- スキルごとに異なる内容を配る手段は設けない。差分が必要になった時点で、それはこの
  ツールの責務ではなく、共通部分とスキル側の薄い設定へ分ける設計の問題である
- ディレクトリ src の配布集合は、表の共通・契約固有 `ignore` でのみ狭められる。
  配布対象を追加する包含パターンや再包含は設けない。ファイル src の明示指定は
  `ignore` の影響を受けない
- 集合は丸ごとメモリに載せて digest する。「共有物は少数・小さい」という既存の規模前提を
  引き継ぎ、大きなバイナリを配る用途は想定しない。ファイル数の上限は設けず、前提が崩れた
  ときに再検討する
- 既に各スキルが手で持っていた古いコピーのうち、dest と別の位置にあるもの(例:
  `scripts/runtime.py`)はどの dest にも属さないためツールは触らない。消すのは利用者の
  仕事である。dest と同じ位置にあるものは条件 3 で取り込む
