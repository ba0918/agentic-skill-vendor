# リリースの仕組み

このツールを npm パッケージ `@ba0918-dev/agentic-skill-vendor` として公開する手順と、
その自動化の設計を記す。

## 方針

人間が判断するのは「いつ・どの版で出すか」だけとする。それ以外(タグ作成・npm への
公開)は機械が行う。承認点を一つに絞ることで、手順の儀式化と半端なリリース
(タグだけあって npm に無い、など)を防ぐ。

release は同時に 1 本だけ走らせ、実行中の run は打ち切らない。2 本が同じ版を読んで、
版を上げたコミットとは別のツリーが publish されるのを防ぐため。打ち切りはタグと
publish の間で run を止めうるが、それはこの設計が防ごうとしている半端な状態
そのものになる。

## 初回リリース(手動)

npm の trusted publishing(OIDC。長期トークンを持たず、GitHub Actions の実行時証明で
publish を認可する仕組み)は、npm 上にパッケージのページが存在しないと設定できない。
そのため初回のみ手動で publish し、その後 npm 側で trusted publisher(このリポジトリと
workflow ファイル名)を登録する。以後の publish はすべて workflow が行う。

## 自動リリース(2 回目以降)

1. 人間: version bump コミットを main に入れる。このコミットには package.json の
   版更新と、CHANGELOG の Unreleased 節の版見出しへの昇格・比較リンクの追加を含める
   (版・変更履歴・タグを 1 操作で揃えるため)。
2. workflow: main への push で bump を検知し、以下を順に行う。
   - package.json の版・既存 git タグ・npm 上の公開済み版を照合し、リリース対象かを決める
   - リリース対象なら通常 CI(型検査・lint・format・テスト・fixture の verify と
     自己完結チェック)を通す
   - 公開する tarball を実際にインストールし、最低対応の Node 20.10 と release が使う
     Node 24、Bun 1.3.x、Deno 2.x から公開 CLI の入口を通す
   - タグ v{版} を作成する(チェックが通った状態にだけタグを打つ)
   - 同じコミットから tarball をビルドし、trusted publishing で publish する

## 照合の分岐と失敗時の挙動

release workflow は main への全 push で動くため、照合は次の 3 つに分岐する。
加えて、照合そのものができなかった場合の出口が 1 つある。

- タグと npm の公開が両方揃っている場合、この push は版の変更を運んでいない
  (リリース済みの版のままの通常のマージ)。リリース対象ではないとして正常終了する。
- タグと npm のどちらか片方だけが存在する場合は、半端なリリース状態としてエラーで
  停止する。黙ってスキップしない。npm は同一版の再公開を許さないため、この状態は
  workflow の再実行の失敗や手作業の混入など人間が見るべき状況であり、緑にして
  流すと隠れる。復旧はこの版をやり直すのではなく、新しい版のリリースで行う。
- どちらも存在しない場合はリリース対象。このとき CHANGELOG に該当する版の見出しが
  あることも確認し、なければエラーで停止する(bump コミットが版・変更履歴・タグを
  1 操作で揃える要件の機械検査)。
- npm への問い合わせが E404 以外の理由で失敗した場合は、照合できていないためエラーで
  停止する。未公開と読み違えるとタグだけが先へ進み、publish が同一版の衝突で落ちて、
  この設計が防ごうとしている半端なリリースを workflow 自身が作ってしまう。この停止は
  状態を何も変えないため、レジストリが答えられるようになってから同じ版のまま再実行
  すればよい(新しい版は要らない)。
- CI が失敗した場合、タグは作られず何も公開されない。修正を積んで bump をやり直す
  (公開済みタグは動かさない。失敗時点では何も公開されていないため、版もタグ名も
  消費されていない)。

## 権限

- workflow は read 権限を基本とし、タグ作成の job にのみ contents: write、
  publish の job にのみ id-token: write を与える。
- publish 前に人間の承認クリック(GitHub Environment の保護)は挟まない。
  承認点は bump コミットに一本化しているため。
